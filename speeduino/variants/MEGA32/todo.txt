MEGA32 RTC improvements - work and test order

Keep changes in the MEGA32 firmware variant wherever possible. Leave shared
Speeduino files and installed libraries unchanged.
Based on STM32 Arduino core 2.6.0 and STM32duino RTC 1.2.0.
Finish each step's checks before moving on. No board testing has been done here.

Terms:
- RTC: date/time clock. It supplies timestamps; it is not the CPU clock.
- LSE: external RTC crystal. LSI: internal clock used as a fallback.
- HAL: ST's hardware-control functions.
- Backup domain: battery-backed RTC settings and saved data. Resetting it can
  erase the date/time and other saved values.
- Valid time: a saved or newly supplied date/time that can be trusted.
- Original code: shared Speeduino code before our RTC changes.
- TXT fix: our earlier proposal to try LSE and fall back to LSI.

Starting measurements and checks:
- Build MEGA32. Record startup time, selected RTC clock, whether saved time
  survives power cycles, and what happens when setting time.
- Test clock failures on the bench, using simulated engine signals.
- Check that normal Speeduino builds do not include MEGA32 replacement files.

1. Record whether the RTC started, which clock it uses, and whether time is valid.
   Status: code written; computer tests pass; board tests still needed.
   See RTC_TESTING.md for the first batch's board tests.
   Reason: improvement to both the original code and TXT fix.
   Keep these three facts separate. Choosing a clock does not prove it started,
   and a running clock does not prove its date/time is correct. Include states
   for not started yet and failed. Do not add monitoring during operation yet.
   Checks:
   - Build MEGA32; compare the reported clock with the hardware's selection.
   - Make sure unset time is distinguishable from valid saved time.
   - Make sure failed setup is never reported as successful.

2. Make the switch to LSI reliable when LSE cannot start.
   Status: code written; computer tests pass; board tests still needed.
   See RTC_TESTING.md. Needs step 1.
   Reason: closes a gap in the TXT fix.
   The TXT fix left the failed external crystal switched on. Changing the RTC
   clock could then make ST's code wait for that failed crystal again and call
   Error_Handler(), which could stop startup. Turn failed LSE off, check that
   it stopped, then start and check LSI before setting up the RTC.
   Check permission to change battery-backed settings, with a time limit.
   Check hardware/library calls for errors that are hidden or stop startup.
   Handle failures inside the variant; do not change the installed library.
   Report RTC unavailable if setup cannot finish, but let the board start.
   Do not reset saved data if the same healthy clock is still being used.
   If a necessary reset loses time, mark it invalid; step 3 improves this.
   Checks:
   - Start with working LSE; restart with the RTC battery connected.
   - Start without working LSE; verify LSI advances and the board starts.
   - Restart with a previously used LSE now unavailable. Verify no second wait
     for the failed crystal during the switch and no Error_Handler() stop.
   - Make each setup/cleanup operation fail in computer tests. Verify failure
     is reported and startup returns. Measure worst-case startup on the boards.

3. Handle saved time and other battery-backed data when changing clocks.
   Status: not completed. Needs steps 1 and 2.
   Reason: applies to both the original code and TXT fix.
   Switching clocks resets the backup domain and can erase time and saved data.
   Check what else uses that data before resetting it. Keep trustworthy time
   where possible; otherwise mark it invalid until new time is supplied.
   Do not blindly trust time from a failed crystal or restore a saved marker
   that says time is valid when the time itself can no longer be trusted.
   Checks:
   - Restart on the same healthy clock without losing saved time.
   - Switch LSI to LSE and LSE to LSI. Check what is kept or marked invalid,
     including other data stored in the backup domain.
   - Losing backup power leaves time invalid; setting time makes it valid again.

4. Stop restarting the RTC whenever the user sets the time.
   Status: the checked HAL code already avoids restarts and crystal retries,
   and checks for failed writes or impossible dates. Full board tests pending.
   Review after steps 1-3.
   Reason: the TXT fix introduced a restart on every update. The original code
   restarted only when time had not already been set.
   Normally write the new date/time using the clock already running. Do not
   repeat crystal startup checks. If the RTC is unavailable, do not falsely
   mark the new time as successfully set. Later crystal failures are step 6.
   Checks:
   - Set time repeatedly through TunerStudio on LSE and LSI. No unnecessary
     RTC restarts, saved-data resets, or repeated crystal startup delays.
   - Check the supplied date/time and validity after updates and power cycles.
   - Check that setting time on an unavailable RTC follows the intended rules.

5. Decide how long startup may wait and when another attempt is allowed.
   Status: not completed. Needs steps 2 and 4.
   Reason: affects both versions; the TXT fix tries LSE on every startup,
   including boards without a working crystal.
   The default LSE attempt can take about five seconds. Measure real boards
   before choosing a time limit; a healthy crystal may start slowly. Keep any
   timeout changes local to MEGA32. Check waits inside library calls as well.
   Avoid repeated attempts during normal operation, and do not restart LSE
   if it is already running properly.
   Checks:
   - Measure fresh starts and battery-backed restarts, with and without LSE.
   - Test slow crystal startup at relevant temperatures and supply voltages.
   - Verify failure waits stay within the chosen limit, and setting time does
     not start another crystal attempt.

6. Detect a crystal that fails while running and recover to LSI.
   Status: not implemented. Needs steps 1-5.
   Reason: neither the original code nor TXT fix watches for this failure.
   Check RTC health without holding up engine work. Confirm a real failure,
   rather than mistaking a normal clock update or busy firmware for one.
   Switch to LSI only when needed, using the cleanup and time rules above.
   Mark time uncertain because we may not know how long the clock stopped.
   Do not simply call the startup code while running: check every recovery
   operation for waits or interrupt changes that could delay engine timing.
   If recovery cannot finish safely, report RTC unavailable and postpone more
   attempts. Do not repeatedly switch clocks or retry forever.
   Checks:
   - Simulate LSE failing after startup. Check detection, recovery or clear
     failure status, and time marked invalid. Recovery must have a time limit.
   - After recovery, LSI advances and setting time restores validity without
     unnecessarily restarting the RTC.
   - Test healthy operation under heavy load for false failure reports. Repeat
     faults to check that retries are limited.
   - Use simulated engine signals to measure any added delays or variation in
     engine scheduling. Compare with the starting measurements and agreed limits.

Final checks after all steps:
- Build MEGA32; shared Speeduino files and libraries remain unchanged.
- Repeat fresh starts, battery-backed restarts, loss of backup power, clock
  changes, missing-crystal startup, time updates, and failures while running.
- Check SD timestamps follow the agreed rules for invalid or unavailable time.
- Record computer/build results separately from board results. A successful
  build does not prove crystal recovery works or engine timing stays correct.
